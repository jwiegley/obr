#+begin_example
Using obr to track work in its own repo makes the pre-commit hook block the next
commit, repeatedly, on a condition that ordinary tracker use creates.

Observed twice in one session, both times mid-commit:

  obr doctor pre-commit: BLOCKED (exit 1, workspace_health=healthy)
  base_jsonl -> warn | Merge anchor <repo>/.obr/merge.base.jsonl is older than the
                       live JSONL

Sequence that produces it, which is just normal use:
  1. `obr close <id>` / `obr create ...`
  2. `obr sync --flush-only` — the surface is rewritten, so the live JSONL is now
     newer than `.obr/merge.base.jsonl`
  3. `git commit` — doctor-quick warns, exits 1, and lefthook blocks

The remedy works and is correctly reported (`obr doctor --repair` -> repaired=true,
"Regenerated stale merge anchor from current JSONL"), but it has to be run by hand
after essentially every tracker flush, and the hook's message does not name it —
it suggests `--repair --dry-run` generically.

Note the reported state is `workspace_health=healthy` while the hook blocks, which
reads as contradictory even though it is accurate: the finding is warn-level, and
as of the obr-rh0 work the hook blocks on any non-zero exit by design.

Worth deciding which of these it is:
  (a) the flush should refresh the merge anchor as part of writing the surface —
      it already has the JSONL in hand at that moment, and leaving the anchor
      behind is what creates the warn;
  (b) the anchor staleness check should tolerate an anchor older than a flush the
      tracker itself performed, rather than treating routine export as drift;
  (c) nothing, and the hook message should name the specific remedy so the
      operator is not left running a generic repair to find out.

(a) looks right to me: nothing else can know the anchor is stale at exactly the
moment it becomes stale. But this is the tracker's own sync contract, so it is a
decision rather than an obvious bug.

Not urgent — it is friction, not data risk, and `--repair` fixes it every time.

John proposed disabling org-hash on these files to stop the :HASH_sha512_256: churn. Measured at the time: that was unsafe, because org-hash was also the only thing writing :MODIFIED: (org-hash-track-mod-time defaults to t), and without a bump obr skipped the edit and the next flush reverted it.

2399abbd removes that dependency for content changes -- an edit is now detected by content even when :MODIFIED: does not move. But the tie-break only sees content_hash 15 fields, so an edit confined to labels, dependencies, comments, or the scheduling and close metadata is still skipped. Editing tags in Emacs is exactly such an edit.

So the decision is: keep org-hash (it bumps :MODIFIED: and therefore covers every field) and land obr-xir so its property stops being deleted; or disable it and accept that label-only hand edits need an explicit obr command.

** Notes

RESOLVED by bb20b64c. The blocker is gone: the equal-timestamp tie is now decided by sync_equals over the whole record, so ANY edit to the file is detected on import regardless of whether :MODIFIED: moved -- including label-only edits, which content_hash could not see.

So disabling org-hash on PLAN.org surfaces is now safe. It also removes the :HASH_sha512_256: churn at the source and makes obr-xir optional rather than necessary.

Keeping org-hash is equally fine; its :MODIFIED: bump simply becomes belt-and-braces rather than load-bearing.

Consequences of a61e826f (obr-m6m) that are correct-by-decision but were not priced,
found by the verification pass. Filing so they are not rediscovered by surprise.

1. TRANSIENT FALSE `degraded` ON BUSY WORKSPACES. Plain `obr doctor` no longer
   serializes against writers, so it can read torn state. Constructed by the
   verifier: three concurrent `obr create` writers (8 issues each) while doctor
   runs produces a transient degraded verdict. Inherent to a lock-free reader; the
   question is whether doctor should retry or label such findings as possibly-torn
   rather than reporting them flatly.

2. `db.write_probe` IS NOW UNSERIALIZED. It executes a rollback-only write
   transaction ("Rollback-only issue write succeeded for ...") while a foreign
   process may hold the workspace lock. SQLite-level locking still applies, but the
   workspace advisory lock no longer guards it. Worth deciding explicitly: either
   the probe acquires the lock for its own duration, or it is skipped when the lock
   is unavailable.

3. `doctor --repair`'s OWN write_lock check still self-collides. Repair does still
   take the lock, so on that path the check reports probe_would_block_live_holder
   on a lock nobody else holds — the original obr-m6m defect, surviving on the
   repair path. The fix is the one originally sketched: surface the acquisition's
   contended/uncontended fact to the check rather than re-probing.

4. BEHAVIOUR CHANGE worth documenting: plain `obr doctor` under a live FOREIGN
   holder now inspects and exits 0, reporting the holder through the probe, instead
   of refusing with concurrency_lost/exit 5. That is what makes the probe
   meaningful, and it follows from the decision, but it is a contract change.

5. Both write_lock reason assertions require OBR_DOCTOR_STALE_LOCK_THRESHOLD_SECS=0:
   a lock file younger than the threshold short-circuits as "not stale" and emits no
   reason at all. That is a second, independent reason the old e2e assertion on
   `persistent_advisory_inode` could never have passed.

including them makes the cache's identity depend on its own enable flag. Benign
for a user who sets it persistently; the reason this fixture cannot express itself.
